## Запуск

1. Запустить Docker Desktop и дождаться работы движка.
2. Если Docker сообщает об отсутствии WSL, установить WSL в PowerShell с правами администратора: `wsl --install --no-distribution`. При запросе Windows перезагрузить компьютер. [Инструкция Microsoft](https://learn.microsoft.com/windows/wsl/install), [инструкция Docker](https://docs.docker.com/desktop/setup/install/windows-install/).
3. В PowerShell 7 (`pwsh`) из корня проекта выполнить:

```powershell
.\prototype\manage.ps1 check
.\prototype\manage.ps1 up
.\prototype\manage.ps1 seed
.\prototype\manage.ps1 test
.\prototype\manage.ps1 restore-check
```

`up` создаёт отдельный проект Compose `av-prototype`, собирает AV-приложение, создаёт сайт `av.localhost` и выполняет миграции. Повторный запуск сохраняет существующие данные. Если создание сайта оборвалось, команда завершается с ошибкой; существующую неполную базу она не стирает. Не удалять volumes для получения зелёного результата — сначала изучить `docker compose ... logs init`.

Интерфейс после успешного запуска: [localhost:8080](http://localhost:8080). Сервис привязан к 127.0.0.1; MariaDB и Redis не публикуют порты на компьютер/локальную сеть. Не использовать среду для реальных финансовых или клиентских данных.

Случайные пароли создаются один раз в `.runtime/prototype.env`; каталог исключён из Git и Docker build context. Имена пользователей: `Administrator`, `sales@av-prototype.invalid`, `pm@av-prototype.invalid`; соответствующие ключи — `ADMIN_PASSWORD`, `AV_SALES_PASSWORD`, `AV_PM_PASSWORD`. Пароли не выводятся в отчёты. `seed` не сбрасывает пароли существующих пользователей и не отправляет приветственные письма.

## Проверяемый пользовательский сценарий P1

1. Под Sales открыть список **Quotation**: учебные Q1 и Q2 относятся к одному синтетическому клиенту. Q2 содержит основной состав M, услуги и штатную строку альтернативы ERPNext. Сумма основного состава — 16 000 USD; налоги исключены только для T1.
2. Открыть **AV Handover**, созданный seed. Зафиксированы ссылка на Q2, основание решения клиента, назначенный PM, состав, условия, сумма и контрольная сумма снимка. Альтернатива остаётся в истории, но отсутствует в принятом составе.
3. Под назначенным PM открыть тот же пакет и нажать **Accept handover**. Создаётся стандартный **Project**. Повторный запрос принятия возвращает существующий проект. До принятия PM может выбрать **Return to Sales** и указать замечания; проект при этом не создаётся.
4. Изменить название/описание M в каталоге под Administrator: исходный коммерческий снимок должен остаться прежним.
5. Попробовать принять пакет под Sales или другим PM, изменить снимок/решение через обычное сохранение. Действия должны отклоняться сервером.

PM принимает пакет передачи; это не подтверждение аванса, не инженерный выпуск и не разрешение закупки. Коррекция отправленного пакета требует новой версии предложения. Этот срез принимает основной состав целого Q2: выбор произвольного подмножества/другой альтернативы непосредственно при передаче ещё не реализован.

## Архитектура и границы

- Используются штатные Customer, Item, Quotation и Project; core Frappe/ERPNext не меняется.
- AV Handover — отдельный DocType приложения `apps/av_platform`. До submit он редактируемый; при submit сервер снимает копию выпущенного предложения. Одна quotation может иметь только один пакет передачи (ограничение базы).
- Назначенный PM принимает или возвращает пакет отдельной серверной операцией. Строка пакета блокируется до конца транзакции; создание проекта и решение записываются вместе, с откатом к savepoint при ошибке. Нет внутреннего commit и фонового создания проекта.
- Коммерческие поля после submit неизменны. Для служебного обновления решения используется внутренняя capability, которую нельзя передать JSON-флагом. Доступ к AV Handover ограничен автором и назначенным PM, дополнительно к правам ролей.
- Штатные роли Sales User/Projects User нужны для операций ERPNext. Их полная пригодность для будущей матрицы V1 ещё не доказана. В этом срезе нет кабинета монтажника и нет доказательств P7.
- Отдельные складские/финансовые журналы, Sales Order, задачи закупки, выпуск и расчёт EAC здесь не создаются. P2–P8 остаются будущей работой.

## Проверки и восстановление

Локальные проверки правил (доступны без Docker, Python 3.13+):

```powershell
$env:PYTHONPATH = Join-Path (Get-Location) 'apps\av_platform'
python -m unittest discover -s tests -v
```

Интеграционные проверки запускаются через `manage.ps1 test` на настоящей Frappe/MariaDB: принятие/повтор, 16 000 и исключение альтернативы, изменение каталога, права другого PM и Sales, подделка служебного обновления, возврат с замечаниями, запрет принятия черновика, уникальность передачи, неизменность снимка и отсутствие проекта при недостаточных правах. 12.11.2026 пройдены 11/11. Конкурентный вызов двумя независимыми соединениями и браузерный сценарий требуют отдельного запуска; наличие блокировки в коде их не заменяет.

`manage.ps1 backup` копирует базу, публичные/приватные файлы и конфигурацию в `.runtime`. `restore-check` создаёт приватный контрольный файл, делает backup, создаёт **новый** сайт `av-restore-<id>.localhost`, восстанавливает базу и файлы штатной командой Bench и сравнивает пакеты, связанные Quotation/Project и содержимое контрольного файла. Ключ шифрования переносится в конфигурацию новой копии. Исходный сайт не перезаписывается; восстановленная копия сохраняется для проверки. Сценарий не доказывает полноту ещё не реализованных складских/финансовых данных P8.

Остановка: `.\prototype\manage.ps1 down`. Данные и резервные копии сохраняются. Автоматическое удаление volumes, сброс сайта и перезагрузка Windows отсутствуют.
