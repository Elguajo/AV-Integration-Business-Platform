Упал `test_seeded_board_shows_card_details` из незакоммиченного `tests/test_card_actions.py` параллельной работы — `review_handover` он не вызывает |

**Дефект и причина (подтверждено C5).** Проигравший одновременный запрос ждёт блокировку строки пакета и после неё видит Accepted, но остальные чтения транзакции идут по снимку MariaDB REPEATABLE READ. Если запрос прочитал что-либо до блокировки, снимок сделан до фиксации победителя, проект в нём не виден, и вызов отвечал HTTP 404. Целостность не нарушалась: второго проекта не было ни в одном запуске.

**Исправление.** В ветке повторного «Принять» право на проект проверяется, только если проект виден в снимке (`frappe.db.exists`). Невидимый проект зафиксирован параллельным «Принять» уже после начала транзакции, с этим PM в участниках; это подтверждает строка пакета, прочитанная с блокировкой.

**Отклонённое первое исправление (`d5833b5`).** Оно перезапускало транзакцию, если `frappe.db.transaction_writes == 0`. Frappe обнуляет этот счётчик при откате к точке сохранения, поэтому в цепочке вызовов первое исправление молча отменяло уже сделанное «Принять» (C6 — FAIL). В рабочем трафике этого не было: каждый HTTP-запрос и вызов MCP — отдельная транзакция.

**Контрольные прогоны C5/C6 на трёх версиях `review_handover`:** исходная `622c3f8` — C5 FAIL, C6 PASS; `d5833b5` — C5 PASS, C6 FAIL; текущая — обе PASS.

Ограничения: C6 во Frappe-тестах не воспроизводится — там отключено управление транзакциями, поэтому проверка есть только в `concurrency-check`. Скрипт не выходит из сессий PM (около 45 за запуск, истекают по сроку). Синтетические пакеты и проекты TP-03 остаются в сайте как история (отправленный пакет удалить нельзя).

## Роли администратора и модератора (ADM-01, 15 ноября 2026)

Поручение пользователя 15.11.2026: «Надо б создать роль модератора и администратора системы». На уточняющие вопросы выбраны «Управляет сотрудниками» (модератор) и «AV-роль поверх System Manager» (администратор). Основание — MVP-SPEC §3, research/04 §19.

- **AV Administrator.** Полное администрирование: роль всегда несёт штатный System Manager (`user_admin.guard_user_change` добавляет его при сохранении User). Деловые решения по-прежнему требуют своих ролей: принять передачу может только AV Project Manager.
- **AV Moderator.** Создаёт учётные записи, включает и отключает их, меняет имя и контакты, выдаёт и снимает рабочие роли `MODERATOR_ROLES` (AV Sales, Sales User, AV Project Manager, Projects User, AV Director). Права на User — через Custom DocPerm (чтение, запись, создание, отчёт; уровень 1 — чтение и запись для таблицы ролей); удаления, экспорта, печати, рассылки, импорта, «поделиться» и входа от имени другого пользователя нет. После входа — список пользователей Desk.
- **Проверка на сервере** (`User.before_validate`, все каналы: форма Desk, REST, `frappe.client.insert`/`delete` строки Has Role, `set_value`, массовая правка): модератор не выдаёт и не снимает иные роли, не меняет учётные записи администраторов, System Manager и других модераторов, не меняет свои роли, профили ролей, пароль чужой учётной записи (включая `change_password`), API-ключи, IP и часы входа, доступ к модулям и число сессий. Сравнение идёт с записью в базе, не с запросом.
- **Найдено при проверке.** `frappe.model.no_value_fields` включает табличные типы; первая версия проверки пропускала дочерние таблицы, и модератор мог бы назначить профиль ролей с System Manager. Исправлено, тест `test_role_profile_is_not_a_way_around`.
- **Следствие.** Первая запись Custom DocPerm для User копирует штатные права DocType на сайте (как DIR-01 для Project/Task/Quotation): будущие изменения прав User в Frappe на этот сайт сами не придут.

## Своя оболочка рабочих мест (UI-04, 15 ноября 2026)

Решение пользователя 15.11.2026 после четырёх колонок навигации на карточке проекта в Desk: «Получается нам мешает Desk... Может быть разработаем свой?», затем «B — своя оболочка». Основание и сравнение — [ADR-006](../.progressive/decisions/ADR-006-own-shell-desk-as-back-office.md) (заменил ADR-004). Задание ui-04-r1.

- **Оболочка** ([localhost:8080/av](http://localhost:8080/av)) — одно приложение Vue 3 + frappe-ui + vue-router, как Frappe CRM. Слева одна панель: «Главная», «Мои задачи», «Все проекты», «Доска работ», «Мои предложения» — только пункты ролей пользователя; внизу «Desk» и меню пользователя с выходом. - **Адреса:** `/av/home`, `/av/my-tasks`, `/av/projects`, `/av/projects/<проект>`, `/av/board`, `/av/sales/<предложение>`. `/av` ведёт на стартовый экран роли; экран чужой роли — тоже на стартовый (данные защищает сервер, не меню).
- **Сервер** (`shell.py`, `www/av.py`): пункты меню, стартовая страница и доступ к Desk приходят в странице `/av`; гость уходит на вход с возвратом на тот же адрес; пользователь без экранов — на свою стартовую страницу (модератор — список пользователей Desk) или в Desk. После входа: Sales → `/av/sales`, руководитель и PM → `/av/home`, монтажник → `/av/my-tasks`.
- **Desk** — back-office: страницы `av-*`, меню AV и иконки AV удалены; `bench migrate` убирает их записи сам (`remove_orphan_entities`). Ссылки на формы документов (Task, Quotation, Project, AV Handover) по-прежнему открывают Desk.
- **Карточка проекта:** две колонки навигации — панель приложения и разделы проекта. Дерева «Вид» нет; фильтр этапов — строка кнопок в разделе «Работы». Боковая панель справа — от 1280 px.
- **Найдено по ходу:** класса `bg-surface-white` в frappe-ui 1.2.0 нет; карточки на главной, в реестре и на доске были прозрачными. Заменён на `bg-surface-base`.

## Запуск

1. Запустить Docker Desktop и дождаться работы движка.
2. Если Docker сообщает об отсутствии WSL, установить WSL в PowerShell с правами администратора: `wsl --install --no-distribution`. При запросе Windows перезагрузить компьютер. [Инструкция Microsoft](https://learn.microsoft.com/windows/wsl/install), [инструкция Docker](https://docs.docker.com/desktop/setup/install/windows-install/).
3. В PowerShell 7 (`pwsh`) из корня проекта выполнить:

```powershell
.\prototype\manage.ps1 check
.\prototype\manage.ps1 up
.\prototype\manage.ps1 seed
.\prototype\manage.ps1 test
.\prototype\manage.ps1 restore-check
```

`up` создаёт отдельный проект Compose `av-prototype`, собирает AV-приложение, создаёт сайт `av.localhost` и выполняет миграции. Повторный запуск сохраняет существующие данные. Если создание сайта оборвалось, команда завершается с ошибкой; существующую неполную базу она не стирает. Не удалять volumes для получения зелёного результата — сначала изучить `docker compose ... logs init`.

Интерфейс после успешного запуска: [localhost:8080](http://localhost:8080) — после входа рабочее место роли на `/av`, Desk — на `/desk`. Сервис привязан к 127.0.0.1; MariaDB и Redis не публикуют порты на компьютер/локальную сеть. Не использовать среду для реальных финансовых или клиентских данных.

Случайные пароли создаются один раз в `.runtime/prototype.env`; каталог исключён из Git и Docker build context. Имена пользователей: `Administrator`, `sales@av-prototype.invalid`, `pm@av-prototype.invalid`, `director@av-prototype.invalid`; соответствующие ключи — `ADMIN_PASSWORD`, `AV_SALES_PASSWORD`, `AV_PM_PASSWORD`, `AV_DIRECTOR_PASSWORD`. Ключ, которого нет в существующем файле, дописывается при следующем запуске `manage.ps1`. Пароли не выводятся в отчёты. `seed` не сбрасывает пароли существующих пользователей и не отправляет приветственные письма.

## Проверяемый пользовательский сценарий P1

1. Под Sales открыть список **Quotation**: учебные Q1 и Q2 относятся к одному синтетическому клиенту. Q2 содержит основной состав M, услуги и штатную строку альтернативы ERPNext. Сумма основного состава — 16 000 USD; налоги исключены только для T1.
2. Открыть **AV Handover**, созданный seed. Зафиксированы ссылка на Q2, основание решения клиента, назначенный PM, состав, условия, сумма и контрольная сумма снимка. Альтернатива остаётся в истории, но отсутствует в принятом составе.
3. Под назначенным PM открыть тот же пакет и нажать **Accept handover**. Создаётся стандартный **Project**. Повторный запрос принятия возвращает существующий проект. До принятия PM может выбрать **Return to Sales** и указать замечания; проект при этом не создаётся.
4. Изменить название/описание M в каталоге под Administrator: исходный коммерческий снимок должен остаться прежним.
5. Попробовать принять пакет под Sales или другим PM, изменить снимок/решение через обычное сохранение. Действия должны отклоняться сервером.

PM принимает пакет передачи; это не подтверждение аванса, не инженерный выпуск и не разрешение закупки. Коррекция отправленного пакета требует новой версии предложения. Этот срез принимает основной состав целого Q2: выбор произвольного подмножества/другой альтернативы непосредственно при передаче ещё не реализован.

## Архитектура и границы

- Используются штатные Customer, Item, Quotation и Project; core Frappe/ERPNext не меняется.
- AV Handover — отдельный DocType приложения `apps/av_platform`. До submit он редактируемый; при submit сервер снимает копию выпущенного предложения. Одна quotation может иметь только один пакет передачи (ограничение базы).
- Назначенный PM принимает или возвращает пакет отдельной серверной операцией. Строка пакета блокируется до конца транзакции; создание проекта и решение записываются вместе, с откатом к savepoint при ошибке. Нет внутреннего commit и фонового создания проекта.
- Коммерческие поля после submit неизменны. Для служебного обновления решения используется внутренняя capability, которую нельзя передать JSON-флагом. Доступ к AV Handover ограничен автором и назначенным PM, дополнительно к правам ролей.
- Штатные роли Sales User/Projects User нужны для операций ERPNext. Их полная пригодность для будущей матрицы V1 ещё не доказана. В этом срезе нет кабинета монтажника и нет доказательств P7.
- Отдельные складские/финансовые журналы, Sales Order, задачи закупки, выпуск и расчёт EAC здесь не создаются. P2–P8 остаются будущей работой.

## Проверки и восстановление

Локальные проверки правил (доступны без Docker, Python 3.13+):

```powershell
$env:PYTHONPATH = Join-Path (Get-Location) 'apps\av_platform'
python -m unittest discover -s tests -v
```

Интеграционные проверки запускаются через `manage.ps1 test` на настоящей Frappe/MariaDB: принятие/повтор, 16 000 и исключение альтернативы, изменение каталога, права другого PM и Sales, подделка служебного обновления, возврат с замечаниями, запрет принятия черновика, уникальность передачи, неизменность снимка и отсутствие проекта при недостаточных правах. 12.11.2026 пройдены 11/11. Конкурентный вызов независимыми соединениями и сбой после создания Project проверяет `manage.ps1 concurrency-check` (TP-03, PASS 14.11.2026); браузерный сценарий требует отдельного запуска.

`manage.ps1 backup` копирует базу, публичные/приватные файлы и конфигурацию в `.runtime`. `restore-check` создаёт приватный контрольный файл, делает backup, создаёт **новый** сайт `av-restore-<id>.localhost`, восстанавливает базу и файлы штатной командой Bench и сравнивает пакеты, связанные Quotation/Project и содержимое контрольного файла. Ключ шифрования переносится в конфигурацию новой копии. Исходный сайт не перезаписывается; восстановленная копия сохраняется для проверки. Сценарий не доказывает полноту ещё не реализованных складских/финансовых данных P8.

Остановка: `.\prototype\manage.ps1 down`. Данные и резервные копии сохраняются. Автоматическое удаление volumes, сброс сайта и перезагрузка Windows отсутствуют.
