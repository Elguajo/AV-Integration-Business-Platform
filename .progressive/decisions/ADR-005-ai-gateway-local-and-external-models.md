# ADR-005 — ИИ: шлюз моделей, локальные и внешние провайдеры, MCP

Status: Accepted
Date: 2026-11-14
Refines: строку «ИИ / MCP» ADR-001 и MVP-SPEC §2.3 (одна учётная запись ИИ для всех каналов)

## Context
Пользователь 14.11.2026: «Как на счет внедрения ИИ через MCP и API как и локальные так и внешние провайдеры. Я планирую установить в офисе сервер туда поставить модельки чтобы они там работали локально и чтобы использовать их через свой собственный веб продукт который сейчас мы создаем». На предложенную схему ответил «Да, записать» (U12).

Проверено 14.11.2026 ([research/04 §13](../../research/04-sources.md#13-ии-шлюз-моделей-и-локальный-сервер-14-ноября-2026)):
- встроенный MCP есть в используемой Frappe 16.55.1: доступен только пользователям Desk, инструменты — поиск, документы, вызов whitelisted-методов с правами пользователя; своего клиента языковых моделей во Frappe нет;
- серверы локальных моделей vLLM и SGLang (Apache-2.0), Ollama и llama.cpp (MIT); шлюз LiteLLM — MIT вне каталога `enterprise/`;
- Raven (AGPL-3.0) и Open WebUI (лицензия с запретом менять брендинг) не встраиваются (ADR-003).

Если чат внутри продукта работает под одной общей учётной записью ИИ, полевая роль через чат увидит то, что ИИ-роли видно, а ей нет (цены, коммерческие вложения). Это нарушает правило «права во всех каналах».

## Decision
- **Шлюз моделей.** Все обращения к моделям идут через один шлюз с OpenAI-совместимым API (кандидат — LiteLLM proxy без `enterprise/`). Продукт знает адрес шлюза и псевдонимы моделей, а не провайдеров. Ключи провайдеров хранятся только в шлюзе. Шлюз ведёт лимиты, учёт затрат и журнал вызовов.
- **Локальные и внешние модели.** Локальные — на офисном Linux-сервере с NVIDIA GPU: Ollama для первых проверок, vLLM для работы многих пользователей. Внешние провайдеры — через тот же шлюз. Выбор модели — после теста на русских запросах по нашим сценариям, не по рейтингам.
- **Маршрут по классу данных.** Сервер определяет, какие данные можно отправлять внешнему провайдеру. Финансы, договоры, цены закупки и персональные данные — только локальная модель. Неклассифицированное по умолчанию считается закрытым. Классификация — настройка (ARC-02), не код.
- **Ассистент в продукте** — код `av_platform` на Python: фоновое задание вызывает шлюз, инструменты — наши whitelisted-методы, ответ приходит через realtime Frappe. Отдельного Node-сервиса для ИИ нет.
- **Учётные записи ИИ.**
  - Чат в продукте работает в сессии человека и вызывает только инструменты из списка, разрешённого ИИ. Его права — пересечение прав человека и роли ИИ.
  - Внешние MCP-клиенты и фоновые задачи работают под отдельным пользователем ИИ с ролью «чтение и черновики»; эта роль не видит данные, которые нельзя отправлять внешнему провайдеру.
- **Классы инструментов.** Чтение выполняется сразу; черновик создаётся сразу с пометкой «создано ИИ»; действие (закупка, инженерная версия, деньги, приёмка) только создаёт «Предложение ИИ», а выполняет его сервер после подтверждения ответственного. Подсказки MCP (`readOnlyHint` и др.) не считаются защитой.
- **Содержимое документов и ответы инструментов** передаются модели как данные; ни одна инструкция из них не выполняет действие без подтверждения человека.
- **Компании (ARC-01).** Настройки шлюза, классификация и журнал принадлежат компании; запрос ИИ не выходит за границу компании.
- Решение определяет способ построения и не расширяет V1. Внедрение — после TP Gate по шагам: MCP и пользователь ИИ → шлюз и локальный сервер → ассистент (чтение и черновики) → «Предложение ИИ».

## Consequences
- Positive: локальные и внешние модели меняются настройкой шлюза; закрытые данные не покидают офис; права ИИ проверяет тот же сервер; клиент продукта выбирает свою схему размещения моделей без изменения кода.
- Cost/risk: офисный сервер — затраты на оборудование и сопровождение; качество локальных моделей на сложных многошаговых задачах может уступать внешним; классификацию данных нужно поддерживать при каждом новом DocType; LiteLLM — внешний сервис со своей поверхностью атаки и обновлениями. Чат в сессии человека уточняет правило «ИИ под отдельной учётной записью» (MVP-SPEC §2.3, AGENTS.md правило 6).
- Revisit when: тест моделей на наших сценариях показывает, что локальная модель непригодна; появляется штатный клиент языковых моделей во Frappe; шлюз меняет лицензию или перестаёт сопровождаться; клиенты требуют только облачного или только локального размещения.
